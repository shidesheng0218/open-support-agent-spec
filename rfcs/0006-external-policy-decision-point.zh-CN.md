# RFC 0006：外部策略决策点（可选的从严接缝）

- **状态：** Draft
- **作者：** OSAS founding maintainers
- **创建日期：** 2026-09-14
- **目标版本：** OSAS v0.4 Draft 候选；对合规性无影响

> **讨论稿。** 在本 RFC 被接受（Accepted）之前，其内容不具规范性，且不得
> 开始任何实现工作（见 CONTRIBUTING.md §RFC 流程）。规范 §5 的确定性
> 算法仍然是唯一与合规相关的决策路径。

## 摘要

本 RFC 提议在规范策略评估算法与外部策略决策点（PDP，如 OPA）之间增加
一条**可选的、只允许从严的接缝**。规范算法对其既有检查保持完全权威；
外部 PDP 只能把决策**调得更严**（`auto_execute → require_approval →
block`)，绝不能放宽。合规性不变：兼容套件仍只测试规范算法。

## 动机

规范 §5 固定了一套确定性评估算法：对租户策略中声明式规则的有序检查，
取最差决策。确定性本身是特性——它让合规可测试——但也封死了表达力。
真实部署中总会遇到放不进 `PolicyRule` 形状的策略：时间窗内的频次限制
（"每客户每天最多 3 笔退款"）、基于证据元数据的复合条件、组织自有的
风险评分、与公司其他基础设施共享的属性规则。

目前的逃生舱口都不是好方案：

- **分叉评估器。** 实现悄悄偏离规范，其合规声明随之失去意义。
- **把策略写进模型提示词。** 这正是 OSAS 要防止的失败模式——用概率性
  手段执行确定性要求。
- **硬塞 rule schema。** 把 `maxAmount` 滥用作频次计数器、把地区字段
  滥用作风险分层。Schema 依旧诚实，策略开始撒谎。

与此同时，通用策略引擎（部署最广的是 OPA/Rego）已经解决了丰富的、
确定性的、可测试的策略评估——并且明确把"对 AI 工具调用的策略强制"
作为营销场景。它们缺的是 OSAS 的领域语义：提案、主体、证据、决策、
审计。显然有价值的组合是：**OSAS 拥有契约；外部 PDP 只贡献更严的决策。**

让这个组合可以被安全标准化的设计约束是：只允许从严的委托。规范检查
（越权、注入、profile 匹配、身份、地区、证据、重复、阈值、永不自动
执行）全部是安全不变量。若允许外部引擎**放宽**它们，一个配置错误的
PDP 就能悄悄关闭规范的安全模型——因此本 RFC 禁止放宽。

## 设计

### 定义

- **规范评估**：规范 §5 算法，即 `@osas/policy-engine` 中
  `evaluateProposal` 的实现。本 RFC 不做任何改动。
- **外部 PDP**：实现自行选择接入的任何策略引擎（OPA、规则服务、内嵌
  WASM 等）。
- **PDP 裁决**:`auto_execute | require_approval | block`，外加实现自有
  命名空间下的可选原因码（见下）。

### 接缝

1. 评估严格按规范 §5 进行，得到规范决策 `D_spec` 及其原因列表。
2. 在规范决策**之后**——且仅当 `D_spec` 不是 `block` 时——实现可以
   咨询外部 PDP，输入文档由实现自行定义并记录（提案、客户、证据摘要、
   策略版本）。
3. PDP 返回裁决 `D_ext`。最终决策取 `D_spec` 与 `D_ext` 在既有严重度
   序（`block > require_approval > auto_execute`）下的**最差者**。
4. PDP 裁决必须携带至少一个原因码。实现自有的原因码**必须**带命名
   空间（如 `OPA_*`、`X_ACME_*`)，使审计读者能将其与规范定义的
   `POLICY_REASON_CODES` 区分开。
5. 每次咨询都要审计：评估对应的 `AuditEvent` 在
   `detail.externalPdp: { system, verdict, reasonCodes, latencyMs }`
   中记录（字段名为示例；确切的审计明细形状属于实现 PR 的一部分）。
   PDP 不可用或超时**必须**按 `block` 处理（失败即关闭），并以
   `PDP_UNAVAILABLE` 风格的原因码记录。
6. 当 `D_spec` 为 `block` 时绝不咨询 PDP；PDP 的裁决也绝不能**放宽**
   决策：若 `D_ext` 轻于 `D_spec`，结果就是 `D_spec`。不存在任何机制
   ——配置、开关或规则——可以委托放宽。

### 本 RFC 不是什么

- 不是规范算法的替代品。以"PDP 会处理"为由跳过规范 §5 检查的实现
  不合规。
- 不是新的决策词汇表。三档裁决保持不变；PDP 将其内部结果（有损地）
  映射到这三档。
- 不标准化输入形状。PDP 输入文档在 v0.4 由实现自定义；若 ≥2 个实现
  收敛，后续 RFC 可标准化最小输入 schema。

### 合规边界

兼容套件只测试规范算法。合规声明（"OSAS 0.x ecommerce-compatible"）
针对的是不挂 PDP 的规范路径。实现可以发布带 PDP 的部署，但：

- 支持声明的合规运行必须能在 PDP 关闭、或被配置为始终返回规范决策的
  情况下复现；
- 能力清单不新增字段（PDP 使用情况不对外宣示，它是内部控制）。

## 兼容性

完全增量、纯可选。无 Schema 变更、无状态机变更、无工具表面变更。
`PolicyDecision` 可携带额外的（带命名空间的）原因码；规范 §5 定义的
原因码集合对实现本就是开放的。

从不挂接 PDP 的实现不受任何影响；参考实现也不会提供 PDP 集成——该
接缝由使用桩（stub）PDP 的契约测试来检验。

## 安全性

- **失败即关闭。** PDP 出错/超时 → `block`。只允许从严 → 被攻破或
  有缺陷的 PDP 最多造成拒绝服务，绝不可能放行规范算法已拒绝的东西。
- **模型不接触凭据（不变）。** PDP 的端点、凭据与策略都在服务端；
  其中任何内容都不进入模型上下文。
- **可审计性提升。** 外部决策成为显式的审计记录，而不是隐形的提示词
  条件。
- **新增攻击面：** PDP 输入文档可能包含客户数据；实现必须对 PDP 输入
  与日志施加与模型上下文同级的 PII 脱敏纪律（规范 §9)。

## 测试计划（接受后的实现 PR)

- `@osas/policy-engine` 中用桩 PDP 的契约测试：从严（PDP 把
  `auto_execute` 提到 `block`)、无操作（`D_ext` ≤ `D_spec`)、PDP 出错
  → `block`、block 时不咨询、原因码命名空间在决策与审计明细中保留。
- 兼容套件：不改动，不挂 PDP 时全部通过。
- 在 `examples/` 中新增一个端到端示例：`evaluateProposal` + 桩 PDP。

## 待定问题

- PDP 裁决的 schema(`decision`、`reasonCodes[]`、可选 `diagnostics`)
  是否值得最小化规范定义，以便在不同 PDP 之间移植？还是 v0.4 完全交给
  实现自定义？
- `PDP_UNAVAILABLE` 是否值得保留为规范原因码？毕竟每个 PDP 集成都会
  用到它。
