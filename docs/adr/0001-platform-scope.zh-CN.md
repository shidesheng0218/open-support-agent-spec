# ADR 0001 — 平台边界：做通用治理控制平面，而不是单一厂商集成

- 状态：已接受（M0）
- 日期：2026-01
- 取代：无
- 适用范围：OSAS 规范 v0.2 Draft、参考实现以及 `packages/` 下的所有包

## 背景

本仓库包含一份规范、一个参考实现，以及若干互不相关厂商的参考适配器。这些适配器端到端验证了安全模型：模型提议、确定性策略引擎决策、只有服务端执行。同时它们也让代码本身无法回答一个问题：

> 这个产品是连接多个系统的治理运行时，还是服务于某一个系统的产品？

这个问题很关键，因为两种答案对应不同的代码组织方式。单一厂商产品可以把厂商概念写进核心 schema、存储和 API；平台不行。

## 决定

**OSAS 是一个与厂商无关的治理平台。** 厂商知识只存在于适配器中。核心契约、治理运行时和控制平面 API 必须保持厂商中立。

按依赖顺序分为四层：

1. **OSAS 规范**——`schemas/` 下的规范性 schema：`ActionProposal`、`Approval`、`AuditEvent`、`CapabilityManifest` 及各 profile。厂商中立。
2. **治理运行时**（`@osas/governance`）——组织、工作区、连接生命周期、事件收件箱、作业队列、对账、案件状态。厂商中立。
3. **适配器**（`@osas/*-adapter`）——唯一允许出现厂商 API 形态的地方。读能力与写能力分别声明。
4. **托管控制平面**——团队协作、托管连接、运维工具与 SLA。不在本仓库内。

## 影响

### 强制约束

- **核心 schema 中不得出现厂商字段。** 厂商 payload 只能作为应用层记录上的不透明快照出现（`IntegrationEvent.payload`），绝不能成为策略引擎据以判断的字段。
- **能力必须声明，不得假定。** 连接声明自己能做什么；未声明的能力会被拒绝而不是尝试执行。读能力与写能力是不同字符串，且写能力必须带凭据引用。
- **控制平面不能执行。** 治理能力列表中不存在执行动作的能力。执行仍然只能经过策略引擎、适配器权限阶梯和服务端内部主体。
- **适配器保持私有包。** 在适配器接口稳定前，厂商适配器不发布到 npm，避免某个 provider 的特殊性意外成为平台公开 API。

### 代价

- 从 provider 事件到动作之间多了一层间接。
- 适配器作者需要把自己的世界映射为厂商中立记录。
- 那些“给某个 provider 加个快捷功能”很容易做的事，必须先在平台层面论证。

这些代价被接受。反过来——核心悄悄依赖某个厂商的平台——后期重构成本高得多。

## 曾考虑的替代方案

**先做单一厂商产品。** 更快达成付费集成，但会让厂商语义变成规范：核心 schema 会吸收厂商字段，策略引擎会编码厂商特例，之后每次集成都等于重写。已否决。

**只做适配器 SDK，不做控制平面。** 把参考实现当库使用，让每个部署自建多租户、队列和审批。已否决：多租户、可靠摄入、重试分类和对账恰恰是容易出错且最需要保障的部分，也正是 OSAS 声称要解决的部分。

**只做规范。** 不再维护运行时。已否决：只有当实现能证明规范时，规范的主张才可信；参考实现也是 schema 变更的验证方式。
