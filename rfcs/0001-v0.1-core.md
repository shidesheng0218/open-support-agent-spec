# RFC 0001: OSAS v0.1 core specification

- **Status:** Draft
- **Authors:** OSAS founding maintainers
- **Created:** 2026-09-05

## Summary

This RFC proposes the complete v0.1 draft of the Open Support Agent Spec (OSAS): a
core domain model for customer-support work, a permission ladder and deterministic
policy engine that gate every agent-initiated mutation, idempotent execution with a
reconciliation path for uncertain outcomes, a 16-tool MCP surface, a model gateway
contract, and the normative security requirements. It is the founding RFC; the full
normative text lives in `docs/spec-v0.1.md` (EN) and `docs/spec-v0.1.zh-CN.md` (ZH),
with the JSON Schemas under `schemas/` as the machine-checkable authority.

## Motivation

Customer-support agents are being wired into helpdesks, commerce platforms, and
billing systems with ad-hoc, vendor-specific integrations. The recurring failure
modes are the same everywhere: models given raw write credentials, free-text
"actions" that cannot be audited, silent double-refunds after retries, and no
uniform answer to "why did the agent do that?".

OSAS addresses this with a single interoperability contract:

1. **All mutations are structured proposals.** An agent never writes directly; it
   creates an `ActionProposal` anchored to evidence, which a deterministic policy
   engine evaluates before anything executes.
2. **A hard permission boundary.** Model principals are capped at
   `request-approval`; only the policy engine / API backend can execute.
3. **Safe failure semantics.** Executions are idempotent by key, uncertain outcomes
   go to human reconciliation, and blind retries are forbidden.
4. **Auditability by construction.** Every step emits an append-only `AuditEvent`.
5. **Vendor neutrality.** The `SupportAdapter` interface isolates the spec from any
   helpdesk/commerce/billing system; the model gateway isolates it from any model
   provider.

## Design

The design is specified normatively in `docs/spec-v0.1.md`; key decisions:

- **Profiles**: `core` (cases, customers, evidence, notes, escalations) plus
  extension profiles `ecommerce` (orders, shipments, refund/reshipment/return/
  cancel actions) and `saas` (subscriptions, invoices, credit balances, credit/
  cancellation/plan-change actions). Action types are profile-bound; mismatches are
  blocked at both schema and policy level.
- **State machines**: explicit transition tables for `CaseStatus` (terminal
  `closed`) and `ProposalStatus` (terminal `policy_rejected`, `rejected`,
  `executed`, `failed`; `reconciliation_required` recoverable only by explicit
  reconciliation).
- **Policy algorithm**: an 11-step deterministic evaluation that collects all
  applicable reasons and resolves to the worst of block > require_approval >
  auto_execute, covering permission overreach, prompt injection, profile mismatch,
  default-deny, reason-code allow-lists, duplicate detection windows, amount
  thresholds, identity verification, region allow/deny lists, and evidence
  sufficiency/freshness.
- **Execution**: keyed by `(tenantId, idempotencyKey)`; replays return stored
  results without side effects; `uncertain` results open reconciliation and a human
  handoff instead of retrying.
- **Tool surface**: 16 MCP tools (`osas_core_*`, `osas_ecom_*`, `osas_saas_*`),
  each with an input schema under `schemas/tools/`; mutation tools only create
  proposals; `executeAction` is never a tool.
- **Model gateway**: tier routing (`classify`/`standard`/`reasoning`), per-task
  output caps, cumulative budget caps, telemetry on every call, and shared
  injection detection feeding the policy engine.
- **Security**: no credentials to the model, injection defense on all untrusted
  text, PII redaction in logs, no blind retries, validate-before-execute, and
  default-deny policy — all normative.

The reference implementation (this repository) realizes the design as a pnpm
monorepo: `@osas/core`, `@osas/schema-validator`, `@osas/policy-engine`,
`@osas/model-gateway`, `@osas/adapter`, `@osas/mock-backend`, `@osas/mcp-server`,
`@osas/api` (Fastify 5, port 3001), `@osas/web` (React 18 + Vite, port 5173), and
the `@osas/compat-suite` conformance suite.

## Compatibility

This is the initial draft; there is no prior version to break. Within v0.x,
subsequent minor versions may be breaking; every persisted object pins
`specVersion: "0.1"` at the schema level so future versions can migrate
explicitly. Independent implementations should treat v0.1 as unstable and target
the compat suite rather than prose.

## Security

The RFC's core purpose is a security boundary for agentic automation; §9 of the
spec is normative. Residual risks accepted in v0.1: the reference implementation is
demo-grade (in-memory storage, no authentication) and MUST NOT be fed real customer
data; injection detection is pattern-based and expected to evolve via future RFCs.

## Test plan

- Unit tests in every package (Vitest, colocated).
- `@osas/compat-suite`: schema valid/invalid fixtures, cross-profile action-type
  rules, tool ↔ adapter ↔ schema 1:1 mapping, state-machine legality tables, the
  policy evaluation matrix (auto-execute small refund; over-threshold → approval;
  unverified identity → block + handoff; stale evidence → approval; blocked region
  → block; model execute-overreach → block; injection → block; duplicate → block),
  and idempotency replay + uncertain → reconciliation with no retry. Emits
  `tests/compat/report/latest.json`.
- `@osas/e2e`: Playwright smoke against `docker compose up` covering console load
  and demo scenario 1 (ecommerce auto refund).
- Runnable examples: the three `/demo` scenarios in the web console (auto refund,
  approval-gated credit, injection/identity handoff).
