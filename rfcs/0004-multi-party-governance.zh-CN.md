# RFC 0004：多方治理模型

- **状态：** Draft
- **作者：** OSAS founding maintainers
- **创建日期：** 2026-09-12
- **目标版本：** 治理层面；在 v1.0 门槛达成时生效

## 摘要

本 RFC 定义在 GOVERNANCE.md 所列 v1.0 门槛达成后取代单一组织托管的治理模型：
设立治理委员会（Governance Committee），由创始维护者团队与每一个在
`conformance/implementations.json` 中持有 `independent-conforming` 注册实现的
组织各占一席，并规定表决规则、商标/兼容性声明政策，以及维护者扩容与退出机制。

本 RFC 仅变更流程，不引入任何 Schema、API 语义或代码。

## 动机

目前所有规范性决策——发布、合并、RFC 接受、路线图——都归创始维护者团队以惰性
共识决定（GOVERNANCE.md §Decision making）。对于发布仅数周的草案规范这很合适，
但它恰恰在本规范自身所主张的维度上封死了可信度：**由无需信任单一厂商的各方来
验证**。RFC 0002 已指出"治理真空被闭源、厂商自证的 guardrails 填满"的风险；
单一厂商的治理模型本质上是同一失败模式向上平移一层。

GOVERNANCE.md 已承诺在 v1.0 时转向多方治理，并要求"具体组成在 v1.0 宣布前由 RFC
定义"。本 RFC 即该约定。在尚无第二家组织持有利益之前定义它，比日后在压力下谈判
更便宜、也更可信。

## 设计

### 委员会组成

1. **治理委员会**取代创始维护者团队，成为发布、规范性产物合并、RFC 接受与
   路线图的决策机构。
2. 创始维护者团队整体持有**一席**，内部以惰性共识行使。
3. 每个在 `conformance/implementations.json` 中持有当前有效的
   `independent-conforming` 注册实现的组织（或独立个人）持有**一席**。同一
   组织的多个实现仍只产生一席。
4. 若实现的注册被移除（声明不实、证据不可复现或主动退出），对应席位自动失效。

### 表决规则

- 日常、非规范性变更（缺陷修复、编辑性文档、测试、工具链）：委员会任意两名
  成员批准，且 CI 全绿。
- RFC 的接受/拒绝：委员会内惰性共识；共识失败时，按席位简单多数表决，且至少
  三席参与投票。
- 对 GOVERNANCE.md 或本模型自身的修改，以及 v1.0 的宣布：需**三分之二席位**
  通过，且除创始维护者外至少一席投赞成票。
- 所有委员会投票记录于公开的会议纪要文件或相关 PR 中。

### 兼容性声明与 OSAS 名称

1. "OSAS"、OSAS 标识（如未来设立），以及 "OSAS <版本> <profile>-compatible"
   这一表述，仅当实现以 `conforming` 或 `independent-conforming` 状态注册于
   `conformance/implementations.json` 且覆盖所声明的 profile 时，才可用于
   描述该实现。
2. 描述性使用（如"实现了 Open Support Agent Spec v0.2"）始终允许，无需注册。
3. 当实现不再满足 conformance/README.md 的证据标准时，委员会可撤销其注册，
   相应声明一并失效。撤销遵循 RFC 表决规则。

### 维护者扩容与退出

- 委员会任何成员可因持续贡献提名新维护者（commit 权限）；由委员会惰性共识
  通过。
- 连续 12 个月不活跃的维护者转为荣休（emeritus）状态（无投票权、无 commit
  权限），可申请恢复。
- 委员会成员可辞职；若辞职方是独立实现者且其实现注册随之失效，则席位失效——
  除非另一组织接手该实现的维护并重新注册。

### 过渡安排

本模型仅在 GOVERNANCE.md 所列三项 v1.0 门槛全部达成时生效。在此之前，现行
单一组织模型不变，本 RFC 仅具指导意义。

## 兼容性

对 Schema、持久化对象、`specVersion`、HTTP API、MCP 工具表面与兼容套件均无
影响。接受本 RFC 的 PR 需同步修订 GOVERNANCE.md（指向本模型），模型生效时再次
修订。

## 安全性

本模型消除了信任故事中的单点故障：兼容性声明不再仅依赖单一组织的一面之词。
商标政策堵住了一个社会工程向量——无证据自称"OSAS 兼容"。技术攻击面无变化。

## 测试计划

纯流程 RFC，无单元测试或兼容套件用例。其依赖的注册标准由 compatibility-claim
issue 模板与 conformance/README.md 的验证流程承载。接受本 RFC 的 PR 必须在同一
PR 中包含 GOVERNANCE.md 修订与 CHANGELOG 条目。

## 待定问题

- 当独立实现者数量增长后，是否应设席位上限或按行业平衡？
- 委员会会议纪要应放在仓内（如 `governance/minutes/`）还是 wiki?
- 12 个月的不活跃窗口是否合适？
