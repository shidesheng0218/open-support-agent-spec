# RFC 0008：与动作绑定的审批

[English](0008-action-bound-approvals.md)

- **状态：** Accepted（已接受）
- **作者：** OSAS 创始维护者
- **创建：** 2026-09-28
- **目标线：** v0.2.x —— 向后兼容的加固性新增；不影响一致性门槛
- **接受出处：** 由创始维护者通过 2026-09-28 已批准的实施方案接受；schema 变更、
  参考实现、测试与中英文档在同一次变更中落地。合并后状态转为 `Implemented`。

## 摘要

Approval 新增可选字段 `actionDigest`：对该审批所批准建议的 `{ actionType, params }`
做规范化（键排序、稳定 JSON）序列化后的 SHA-256。执行边界在执行前用即将执行的
建议重新计算摘要，两者不一致即拒绝执行——由此关闭"人批准了这个"与"实际执行的是
这个"之间的检查与使用时机（TOCTOU）缺口。该模式借鉴自微软 AGT 的
`enforced_identity`（ADR-0030），本 RFC 将其适配到 OSAS 现有的审批生命周期与
审计链上。

## 动机

今天，一份审批授权的是一个*建议引用*，而不是一个*动作*。在"决定"与"执行"之间，
有三件事可能悄悄分叉：

1. **存储被篡改或损坏。** 建议的 `params` 在审批后被原地修改（存储 bug、存储被
   攻破、误迁移）；随后执行的是一个没人批准过的动作。
2. **接线错误。** 有 bug 的集成拿着建议 A 的审批，却执行了建议 B。
3. **审计歧义。** 对一笔执行提出异议时，人的决定与确切的动作输入之间没有密码学
   链接——只有两行互相*引用*的记录。

OSAS 已经关闭了陈旧审批漏洞（审批 fail-safe，威胁 T13：超时仅允许拒绝）。但一份
*未过期*却授权了*另一个*动作的审批仍然可能发生。深度竞品分析
（docs/competitive-deep-dive.md §3.1）把它识别为对 AGT 最清晰的一项能力差距——
AGT 的 ADR-0030 把每份审批绑定到 `SHA-256(JCS(动作输入))`，并在执行时用七项原子
检查重新校验。OSAS 不需要 AGT 的全套链式条目机制来获得这个核心性质；它只需要
一个摘要，盖一次，校验一次。

如果什么都不做：每一个"这是人批准的"叙事都建立在可变行的引用完整性上——这是
OSAS 存在所要治理的那类动作（动资金的写操作）审计链上最薄弱的一环。

## 设计

### 摘要

`actionDigest = 小写十六进制( SHA-256( UTF-8( stableJSON({ actionType, params }) ) ) )`

- `stableJSON` 完全复用审计哈希链已规定的规范化（规范 §12.3，
  `docs/implementing-osas.md` "复现审计哈希链"一节）：键按 UTF-16 码元排序，
  无空白，不做任何字段剔除。
- 摘要覆盖的是**被批准时**的建议——即转换前的 `params`。参数 transforms
  （规范 §5）是执行时应用的确定性策略改写；它们不改变人所批准的内容，因此
  不改变摘要。
- 摘要**不**单独覆盖 `caseId`/`amount`：只有当实现把金额放进 `params` 时它才
  属于规范化动作输入。（v0.2 参考实现：`params` 承载动作载荷；`amount` 在顶层
  镜像一份供策略求值。见"开放问题"。）

### 盖章（创建时）

当策略决策为 `require_approval` 时，服务端创建 `Approval` 时即写入由该建议
计算的 `actionDigest`（规范 §2.6 新增该字段；`schemas/core/approval.json` 新增
可选 `actionDigest`，匹配 `^[0-9a-f]{64}$`）。自动执行的建议**没有**审批对象，
不受影响——它们的门禁是策略决策本身，已盖在 `proposal.policyDecision` 上。

### 校验（执行时）

`executeProposal` 新增可选的绑定参数。调用方提供 `actionDigest` 时，引擎**必须**
用传入的建议重新计算摘要，并在两者不一致时**在任何状态迁移、重放查询、transform
或适配器调用之前**抛出 `ActionBindingMismatchError`（`ACTION_BINDING_MISMATCH`）。
未提供摘要时（本 RFC 之前创建的旧审批，或未带绑定使用引擎的嵌入方）跳过该校验——
字段是可选新增，既有行为不变。

API 执行路径会加载该建议的已决定审批并始终携带绑定，因此对经由 API 的执行该校验
是无条件的。不匹配会审计为 `action_binding_mismatch_blocked`（新增 AuditEventType），
并向调用方返回 409 `ACTION_BINDING_MISMATCH`。建议**不做**状态迁移；分歧必须由人
复核（建议可以被拒绝并重新创建）。

### 一次性消费

已由现有机制覆盖：执行成功后建议进入终态（`executed`/`failed`），状态守卫拒绝
对非 `approved` 建议的再次执行，且 `(tenantId, idempotencyKey)` 存储重放无副作用。
本 RFC 不新增消费机制；它绑定的是这一次被允许的执行**是什么**。

### 与审批 fail-safe 的关系

正交且互补：过期（T13）约束审批*能活多久*；绑定约束它*授权什么*。过期在决定时
求值；绑定在执行时求值。一份审批必须同时通过两者。

## 兼容性

- **Schema：** `approval.json` 新增一个可选字段；`audit-event.json` 的 `eventType`
  枚举新增一个取值。两者均为新增式变更，先前合法的文档仍然合法。
  `additionalProperties: false` 意味着旧的严格校验器会拒绝携带 `actionDigest` 的
  *新*文档——在 v0.x 期间可接受（按 GOVERNANCE.md 的 minor 线演进规则），且共享的
  `schemas/` 目录让仓内实现保持一致。
- **一致性：** 不变。黑盒 runner 本轮不新增检查；该性质由引擎强制并由白盒测试
  证明。未来的一致性 profile 可以探测它。
- **API/MCP 面：** 不变（执行路径新增一个错误码）。
- **已持久化对象：** 本 RFC 之前创建的审批没有 `actionDigest`，继续可用
  （跳过校验）。

## 安全

- **关闭：** 审批/执行的 TOCTOU、错建议接线、已批准写操作的审计歧义（邻近威胁
  类别 T6/T8；威胁模型新增一条对应条目）。
- **不引入新凭据或秘密**；摘要由内容推导。
- **算法敏捷性：** SHA-256 + 稳定 JSON，与审计链同一原语；如未来确需迁移，可由
  后续 RFC 为摘要加版本前缀（`sha256:…`）。
- **拒绝服务说明：** 能破坏存储的攻击者现在可以触发执行拒绝——但拒绝是安全的
  方向（失败即关闭），而且这种攻击者本来就已经输给审计哈希链。

## 测试计划

- `@osas/policy-engine`（白盒）：
  - 摘要确定性、与键序无关；
  - 篡改 `params` → 在任何适配器调用之前抛 `ActionBindingMismatchError`
    （适配器调用数保持 0）；
  - 摘要匹配 → 正常执行；
  - 无摘要 → 跳过校验（向后兼容）；
  - 过期判定在决定时仍优先生效（既有 T13 测试不受影响）。
- `@osas/api`：批准建议时写入 `actionDigest`；摘要匹配的执行通过；不匹配的以
  409 `ACTION_BINDING_MISMATCH` 拒绝，并恰好产生一条
  `action_binding_mismatch_blocked` 审计事件。
- 兼容套件：不变且保持通过（不新增黑盒检查）。

## 开放问题

- 规范化输入是否应显式包含顶层 `amount`（当前它在顶层参与求值，而摘要覆盖
  `params`）？若未来 schema 版本把金额移入 `params`，摘要定义保持不变。
- v1.0 时 `actionDigest` 是否应对新审批改为必填？（建议是；v0.x 为兼容保持可选。）
